## 1. Что это и для кого

Инструмент для **одного человека — ведущего** деловой игры. Игроки (фирмы) сообщают
ему свои решения вне приложения: устно, в чате, на бумаге. Ведущий вводит их,
запускает расчёт и получает готовые к рассылке отчёты.

Ключевая потребность, вокруг которой всё построено: **после расчёта периода быстро
получить отдельный отчёт по каждой фирме и разослать его именно этой фирме**, не
раскрыв чужие решения и P&L, плюс один общий отраслевой отчёт, который видят все.

Технически это локальное React-приложение: ни сервера, ни базы, ни авторизации.
Весь расчёт идёт в браузере, состояние живёт в `localStorage`.

Актуальный состав и число тестов показывает `npm test`; исторические численные
оценки размера проекта не являются критериями корректности.

## 2. Быстрый старт

```bash
npm install
npm run dev        # http://localhost:5173
```

| Команда | Что делает |
|---|---|
| `npm run dev` | dev-сервер на `127.0.0.1:5173` |
| `npm test` | тесты движка, отчётов и хранения, включая нативные контрольные данные |
| `npm run test:watch` | тесты в режиме наблюдения |
| `npm run typecheck` | проверка типов без сборки |
| `npm run build` | продакшен-сборка в `dist/` |
| `npm run smoke` | прогон партии в реальном Chrome (нужен поднятый `npm run dev`) |

Сборка — статика: `dist/` можно открыть с любого статического хостинга или просто
раздать файлами.

> **Про `127.0.0.1`.** В `vite.config.ts` сервер явно привязан к IPv4. По умолчанию
> Vite на Windows слушает только IPv6-loopback (`[::1]`), из-за чего часть
> инструментов не достукивается по `127.0.0.1`.

## 3. Как вести партию

### 3.1. Создание лиги

Экран **«Лиги»** → название, число фирм (2–12) → «Создать». Приложение сразу
открывает настройки.

### 3.2. Настройка

Экран **«Настройки»** — три блока:

- **Фирмы и стартовые условия.** Названия, станки, наличные, займы, капитал, склад.
  Приложение проверяет тождество стартового баланса и предупреждает красным, если
  оно не сходится: `наличные + склад + станки × стоимость = займы + капитал`.
  После расчёта первого периода состав фирм и их стартовые условия блокируются —
  иначе разъедутся уже посчитанные периоды.
- **Версии формул** — шесть переключателей спорных мест (см. [раздел 6](#6-разрешённые-развилки-и-флаги)).
- **Константы движка** — всё, что в источниках названо параметрами конкретной
  партии (см. [раздел 8](#8-справочник-конфигурации)).

### 3.3. Раунд

Экран **«Период»**:

1. Таблица решений — по строке на фирму. Поля идут в порядке, который рекомендуют
   игроки-практики: **цена → производство → маркетинг → инвестиции → НИОКР**.
   При наведении подсказки: 80% загрузки (оптимум себестоимости) и размер
   амортизации (минимум инвестиций, чтобы мощность не упала). Под каждым полем —
   мелким серым значение прошлого периода, для сравнения.
2. Последняя колонка — **бюджет нативного диалога ввода** (`ui/fundsPreview.ts`),
   а не нижняя граница итоговой ликвидности. Из наличных и остатка кредитной
   линии вычитаются только производство, маркетинг, нетто-инвестиции и НИОКР.
   Амортизация возвращается в бюджет, в том числе при нулевых/отрицательных
   брутто-инвестициях. Raw-себестоимость не округляется до центов: каждое из
   четырёх подписанных слагаемых отдельно усекается к нулю. Кредит может быть
   отрицательным, если заём уже выше предела; сначала расходуются наличные.
   Подсказка показывает амортизацию, нетто-инвестиции и раздельные остатки.
   Цвет: зелёный — остаток не меньше 15% начальных средств, жёлтый — меньше,
   красный — отрицательный бюджет (кнопка расчёта блокируется).
   **Это не гарантия итоговой ликвидности:** увольнения, хранение, проценты,
   налоги и выручка учитываются в расчёте периода отдельно. Подробнее:
   `docs/native-entry-budget.md`. Saved-история и opening-балансы не пересчитываются.
3. Макропараметры периода и свободный новостной текст, который увидят все фирмы.
4. **«Рассчитать период N»**.
5. Внизу появляются вкладки: отраслевой отчёт, сводный отчёт (только для
   ведущего) и по одной на каждую фирму. У каждой — «Копировать текст» и
   «Скачать как изображение». Галочка «с отраслевым блоком» решает, приклеивать
   ли общий блок к личному отчёту.
6. Под отчётами — сводная таблица периода для самого ведущего.

Партия сохраняется автоматически после каждого расчёта. **«Откатить период N»**
удаляет результаты последнего периода, оставляя решения — можно поправить и
пересчитать.

### 3.4. История

Экран **«История»** — таблица по всем периодам: цена, заказы, выручка, чистая и
накопленная прибыль, наличные, РИФ. Плюс сводка по индустрии с изменениями к
предыдущему периоду.

**Главный архитектурный принцип:** движок ничего не знает про интерфейс и способ
ввода решений. Всё общение с ним идёт через одну функцию:

```ts
computePeriod({
  periodIndex, config, macro, firms, opening, decisions, previousIndustry
}): PeriodResults
```

Благодаря этому личные кабинеты игроков, онлайн-мультиплеер или ИИ-соперники можно
добавить позже, не трогая расчёт.

Стек: React 18, TypeScript, Vite, Zustand, Vitest, `html-to-image`.

## 5. Игровой движок: формулы

### 5.1. Порядок фаз

```
1. Решения                    5 параметров на фирму
2. Спрос                      → ordersReceived_i
3. Инвестиции и мощность      → depreciation, capacityNext, амортфонд
4. Себестоимость              → unitCost_i
5. Продажи                    → sold, unfulfilled, inventoryEnd
6. P&L                        → netProfit
7. Кэш-флоу и заём            → cash, loan
8. Баланс                     → проверка тождества
9. РИФ и отраслевые агрегаты
```

> **Отступление от ТЗ.** В ТЗ инвестиции стоят пятой фазой, после себестоимости.
> Но формула себестоимости версии Б требует мощность **следующего** периода,
> поэтому инвестиции считаются раньше. Данные для них зависят только от решений и
> входящего состояния, так что перестановка — вопрос порядка вычислений, а не
> изменение модели.

### 5.2. Спрос: сколько заказов приходит на лигу

Расчёт откалиброван реверс-инжинирингом сейвов и истории 65 реальных партий
(`mecom-spec.md`), а не восстановлен по конспекту, как раньше. Кривая сразу
даёт итог **по отрасли**, а не «на фирму» — для однородной лиги (все по одной
цене):

```
D(P) = 60850 / P^0.85     при P ≤ 39.6
     = 1668820 / P^1.75   при P > 39.6
```

Два степенных режима, точка стыка ≈39.6 — натуральное пересечение обеих ветвей
при этих коэффициентах (те же ≈39.6, что и раньше). `Всего_заказов = D(P̄)`, где
`P̄` — обычное среднее арифметическое цен по лиге; **на N домножать не нужно** —
разброс между фирмами задаёт только дележ долей на стадии Б (раздел 5.3), сумма
которых по лиге равна 1.

> **Исправленная ошибка калибровки.** Раньше коэффициенты (7607 / 208361) были
> откалиброваны как «заказов на фирму» на восьмифирменных прогонах, и код
> домножал результат на `N`. Это работало только случайно совпадая при N=8 —
> при других N (например, N=2) отраслевой итог получался в разы меньше нужного
> (N=2 давал вчетверо меньше, чем N=8, при той же цене). Коэффициенты
> пересчитаны напрямую на уровне отрасли по тем же замерам, деление на N из
> формулы убрано; регрессия в `demand.test.ts` («breakdown.priceDemand не
> зависит от числа фирм в лиге») фиксирует это на будущее. Итоговый объём
> рынка `D` при этом намеренно зависит от N через отдельные множители масштаба
> лиги (см. раздел 2.3 `mecom-spec.md`) — это не регрессия того же бага.

Максимальное отклонение от факта на 8 замерах — 0.56%. Разброс цен внутри лиги
сам по себе почти не влияет на объём — проверено для `P̄ ≤ 40` (при разбросе
±20 отклонение всего 2%). Выше точки перелома формула даёт известное, но не
откалиброванное смещение (до +20% при сильном разбросе и высокой средней цене)
— источник прямо говорит, что для клона это воспроизводить не обязательно.

Сверху на `D(P̄)` домножаются ещё два множителя масштаба лиги (мекомspec 2.3,
«Шаг 3»), оба — эффект по лиге целиком, а не отдельной фирмы:

```
D = D(P̄) · max(0.1, 1 + 0.0000224 · Σ ЗатухающийЗапас_i(t)) · множитель_маркетинг(ΣM)

множитель_маркетинг(ΣM) = [−2.4507 + 0.3798·ln(ΣM + 879)] / [−2.4507 + 0.3798·ln(9279)]
```

Суммарный маркетинг лиги за текущий период (не накапливается, важна только
сумма `ΣM`, не распределение между фирмами) расширяет категорию
логарифмически, с насыщением.

> **Два разных счётчика НИОКР — не путать.** У НИОКР в игре два независимых
> эффекта, и здесь легко ошибиться, объединив их в один счётчик (это и была
> исправленная ошибка калибровки этого раздела):
>
> 1. **Доля рынка между фирмами** (раздел 5.3 ниже) — вечный накопленный
>    счётчик `rndCumulative`, который никогда не уменьшается. Ранний вклад в
>    НИОКР даёт преимущество в доле на всю игру.
> 2. **Объём всего рынка** (этот раздел) — отдельный, ЗАТУХАЮЩИЙ запас
>    `rndDecayStock`. Каждый период в него кладётся не сырая трата, а избыток
>    над нормой `demandRndPeriodNorm` (дефолт 420):
>    ```
>    Избыток_i(t)        = НИОКР_i(t) − 420
>    λ_i(t)               = 1 − 1/(1 + НИОКР_i(t) / demandRndDecayScale)   # дефолт scale=25000
>    ЗатухающийЗапас_i(t) = λ_i(t) · ЗатухающийЗапас_i(t−1) + Избыток_i(t)
>    ```
>    `λ` пересчитывается каждый период от ТЕКУЩЕГО вклада фирмы — крупный
>    разовый всплеск тает медленно, а как только траты возвращаются к норме,
>    остаток запаса забывается быстро (λ мала при малых тратах). Если фирма
>    тратит меньше нормы, избыток отрицателен и запас может уйти в минус —
>    ожидаемо, такая фирма слегка тянет общий рынок вниз. `max(0.1, ...)` —
>    защитный пол от отрицательного объёма заказов, а не откалиброванное
>    значение: он страхует только затяжное глубокое недоинвестирование всей
>    лиги разом, что не встречалось в калибровочных партиях.
>
> Калибровочная точка (оба множителя = 1) — Σ запаса = 0 (все фирмы тратят
> ровно норму без предыстории) и `ΣM = 8400` (дефолтный маркетинг вводного
> сценария N=8). В отличие от `D(P̄)` выше, итоговый объём рынка **зависит от
> N** через эти два агрегата — см. врезку выше про исправленную ошибку
> калибровки `D(P)`, это другой механизм того же класса.

### 5.3. Спрос: как заказы делятся между фирмами

```
доля_i = w_м · m̂_i + w_ц · p̂_i + w_н · n̂_i        (веса по умолчанию 15% / 70% / 15%)
```

**Маркетинг** — степень 1.5, БЕЗ деления на цену и БЕЗ накопления между периодами:

```
m̂_i = M_i^1.5 / Σ M_k^1.5
```

**НИОКР** — линейно, накапливается за всё время игры, включая базовый уровень
вводного периода (`initialRnd`, дефолт 420):

```
n̂_i = N_накопл,i / Σ N_накопл,k
```

**Цена** — ядро `f(P)` (калиброванная таблица с линейной интерполяцией) за
вычетом доли среднего по лиге:

```
p̂_i = x_i / Σ x_k,   x_i = f(P_i) − λ · f̄        (λ = 0.2076 по умолчанию)
```

Вычитание `λ·f̄` — ключевая особенность: `x_i` может быть отрицательным, тогда
дорогая фирма не просто мало получает, а уменьшает общую привлекательность
рынка и «отдаёт» заказы остальным. Именно это порождает наблюдаемую
немонотонность — у дорогих фирм заказы сначала падают, потом растут по мере
роста числа дешёвых конкурентов. Ядро `f(P)` в диапазоне 20–40 близко к
`(30/P)^2.7`, выше 40 круче, около `P≈74` проходит через ноль; точки 65–95 не
измерялись, там интерполяция грубая.

Если по какому-то каналу никто ничего не вложил, его доля делится **поровну** —
заказы этого канала всё равно приходят на лигу и должны кому-то достаться
(иначе деление на ноль). Никакого отдельного штрафа/потолка цены здесь больше
нет: эту роль естественно выполняет убывающее (и уходящее в минус) `f(P)`.

Расхождение с игрой у эталонной реализации — нигде не больше 5 заказов на
фирму, в большинстве партий 0–1.

### 5.4. Себестоимость единицы

Единая откалиброванная формула (совпадает на всех замерах проверочного сценария):

```
Себест_ед = costK1 · (мощность_баз / мощность_тек) + costK2 + A

A = (CU − CUopt)² / costCuUp      при CU > CUopt
  = (CUopt − CU)² / costCuDown    при CU < CUopt
```

`мощность_баз` — стартовая мощность фирмы (период 0), `мощность_тек` —
«полная мощность» текущего периода, `CU = 100 · производство / мощность_тек`.
Дефолты: `costK1=15`, `costK2=3`, `CUopt=80`, `costCuUp=10000/69`, `costCuDown=10000/138`.
Для нерастущей фирмы на ровно 80% загрузки даёт ровно $18. `costCuUp/costCuDown`
— параметры конкретного сценария, а не константы движка (в стороннем разборе
встречались 147 и 73.5).

### 5.5. Инвестиции и амортизация

Решение игрока «Инвестиции» — это **инвестиции-брутто**: они сперва покрывают
амортизацию, остаток идёт на новые станки («остаточный принцип»).

```
Амортизация      = станки × (стоимость_станка / срок_службы)     # 40/20 = $2 за станок
Инвестиции_нетто = Инвестиции_брутто − Амортизация
Пул              = Инвестиции_нетто + Остаток_амортфонда_с_прошлых_периодов
Новые_станки     = floor(Пул / 40)                                # может быть < 0
Остаток_амортфонда = Пул − Новые_станки × 40
Мощность_след    = станки + Новые_станки
Капвложения      = Мощность_след × 40 + Остаток_амортфонда
```

При недоинвестировании (`Инвестиции_брутто < Амортизация`) станки разбираются на
запчасти и мощность падает — `floor` корректно работает и для отрицательного пула.

### 5.6. P&L

```
Выручка       = Цена × Продано
СЕБЕСТ        = средневзвешенная_себестоимость × Продано
Валовый доход = Выручка − СЕБЕСТ

средневзвешенная = (Склад_old × Себест_old + Произведено × Себест_new)
                 / (Склад_old + Произведено)

Штраф за увольнения = 10 × max(0, Занято_прошлый − Занято_текущий)
Стоимость хранения  = 1 × (единицы, пролежавшие ВЕСЬ предыдущий период)

Банковский процент  = Займ_в_пределах_лимита × (осн.ставка + 1%) / 4
                    + Займ_сверх_лимита      × экстр.ставка      / 4

Прибыль до налога = Валовый доход − Маркетинг − НИОКР − Амортизация
                  − Штраф − Хранение − Банк.процент

Налог          = ставка × max(0, Прибыль до налога)
Чистая прибыль = Прибыль до налога − Налог
```

Два принципиальных момента:

- **Хранение — с задержкой в один период.** Платим только за то, что пролежало
  полный предыдущий период; свежепроизведённое не считается.
- **База банковского процента зависит от режима финансирования.** В стандартном
  для новых игр режиме `preRevenue` сначала рассчитывается долг, необходимый для
  расходов до выручки; процент начисляется на этот долг, а отдельный поздний
  докредит для кассового разрыва в базу процента этого периода не входит. Это
  проверено на нативных SAVE HERMES1. В архивных режимах `none` и `sweep` процент
  согласуется с закрывающим займом итеративным пересчётом P&L/кэш-флоу
  (`resolvePnlAndCashFlow`, обычно 2–4 повтора).
- **Отрицательный заём — это депозит.** При `featureFlags.loanRepayment:
  'sweep'` погашение (раздел 5.7) не останавливается на нуле — заём может уйти
  «в минус». Банковский процент в этом случае — ДОХОД, а не расход: считается
  по отдельной ставке `config.depositRate` (дефолт 10% годовых) от суммы
  депозита, без тарифных траншей и лимитов займа. `computeBankInterest`
  возвращает для этого случая отрицательное число — знак сам разворачивает
  вычитание в P&L и кэш-флоу в прибавку, без отдельных веток у вызывающего кода.

### 5.7. Кэш-флоу и кредитная линия

Заём — не решение игрока, а автоматическое финансирование. В новых играх
используется `preRevenue`: до получения выручки долг меняется на разницу между
бюджетом (производственные затраты + маркетинг + НИОКР + инвестиции-брутто −
амортизация + штраф увольнения) и входящими наличными. Этот первый долг может
погашать уже существующий заём; процент начисляется на него. Если после расчёта
P&L денег всё ещё не хватает, поздний top-up кредита учитывается отдельно.
Алгоритм проверен на нативных SAVE HERMES1; подробности и границы — в
[CALIBRATION.md](CALIBRATION.md).

Ниже приведена формула архивного режима `none`:

```
ДП = Выручка − Произведено × Себестоимость − Маркетинг − НИОКР
   − Инвестиции_брутто − Штраф − Хранение − Банк.процент − Налог

новый_заём = max(0, −(Наличные_вход + ДП))
Наличные   = max(0, Наличные_вход + ДП)
Займы      = Займы_вход + новый_заём
```

В режиме `none` заём **не гасится автоматически** — поэтому фирма может
одновременно иметь крупный кэш и крупный долг (именно так в реальном отчёте
RLC). Режим оставлен для старых партий и пользовательских сценариев; старые
сохранения без поля `loanRepayment` продолжают загружаться как `none`.

В альтернативном режиме `sweep` гасится **избыток
ВХОДЯЩЕГО кэша сверх затрат этого периода** (себестоимость произведённого,
маркетинг, НИОКР, инвестиции-брутто, штраф, хранение, банк.процент, налог —
всё, кроме выручки). Выручка ЭТОГО периода в гашение не идёт — она осядет в
кэш и станет «лишней» только со следующего периода. Это НЕ то же самое, что
«гасить из положительного денежного потока периода» (тот включает выручку) —
разница принципиальна: на реальном отчёте RLC входящий кэш ($47 910) был
МЕНЬШЕ затрат периода без выручки (~$64 520), избытка не было вообще, и по
формуле «избыток входящего кэша» заём не должен был гаситься — ровно как в
отчёте. Поэтому `'sweep'` по этой формуле не расходится с RLC (в отличие от
более простой и неверной формулировки «гасить из ДП»), а на других партиях
объясняет то же наблюдение, что и раньше: наличные почти не растут при
стабильной прибыли, потому что входящий избыток каждый период уходит в долг,
а сама выручка ещё период «дозревает» до статуса избытка — см.
[раздел 6](#6-разрешённые-развилки-и-флаги).

Погашение не останавливается на нуле займа — если избытка больше, чем весь
заём (или заём уже отрицательный), остаток продолжает уходить в минус: заём
становится или растёт как **депозит**, на который дальше начисляется доход по
ставке `depositRate` (раздел 5.6). Если в каком-то периоде наступает кассовый
разрыв, депозит сначала расходуется на его покрытие («новый заём» из формулы
раздела 5.7 в этом случае — просто уменьшение отрицательного `loan`), и лишь
когда депозита не хватает, фирма уходит в настоящий положительный долг — без
отдельного кода: и депозит, и заём — один и тот же знаковый остаток `loan`.

В кэш-флоу фирма платит **полную стоимость произведённого**, а в P&L списывается
себестоимость только проданного — отсюда расхождение прибыли и движения денег.

### 5.8. Баланс

```
Актив  = Наличные + Склад × средневзвеш.себестоимость + Капвложения
Пассив = Займы + Накопленная прибыль + Капитал

Тождество: Актив == Пассив + Капитал
```

Выполняется **по построению**: `Δактив = ЧП + Δзайм`, что в точности равно
`Δнакопленной прибыли + Δпассива`. Проверка `assertBalanceIdentity` с допуском $1
стоит в каждом расчёте и падает с внятной ошибкой, а не молча искажает цифры.

### 5.9. РИФ — рейтинговый индекс фирмы

Сумма шести критериев, откалибрована реверс-инжинирингом (совпадение 100% на 32
фирмах в 4 партиях по итогу и по каждой компоненте):

```
РИФ_i = C1 + C2 + C3 + C4 + C5 + C6
```

**Критично:** каждая компонента округляется до целого ОТДЕЛЬНО (половина вверх),
и только потом суммируется — если сложить и округлить в конце, результат
разойдётся с игрой.

| № | Критерий | Формула | Вес по умолчанию |
|---|---|---|---|
| C1 | Н.Приб | `w1 · НакопПриб_i / (t · НакопПриб_база)` | 50 |
| C2 | ПотСпр | `min(w2 · P_i / avg(P), 2·w2)`, `P_i = маркетинг_i + НИОКР_i + P_перенос` | 10 |
| C3 | ПотПр. | `w3 · S_i / avg(S)`, `S_i = произв_i + произв_i,пред` | 10 |
| C4 | Эфф80% | `(w4/10) · Eff(CU_i)` | 10 |
| C5 | Доля Р | `w5 · доля_i / (100/N)` | 10 |
| C6 | Рост | `w6 · доля_i / доля_i,пред` | 10 |

`t` — номер периода (вводный = 1). `доля_i` — доля рынка **в штуках
проданного**: `100 · сбыт_i / Σсбыт` (не в заказах!). `avg(...)` — обычное
среднее арифметическое по всем фирмам лиги за текущий период. `НакопПриб_база`
и `произв_i,пред`/`доля_i,пред` фиксируются/переносятся из периода 0 и
предыдущего периода соответственно; `P_перенос` — параметр сценария (по
умолчанию 0). В периоде 0 критерий «рост» равен базе `w6` (предыдущего периода
нет), а базой критерия 1 служит накопленная прибыль этого же периода — разница
нулевая, критерий даёт ровно `w1`.

`Eff(CU)` — отклонение загрузки мощности от оптимума 80%:

```
Eff(CU) = 9.88 − 0.136·(CU − 80)             при CU ≥ 80
        = 9.88 − 0.102·(80 − CU)             при 30 ≤ CU < 80
        = 9.88 − 5.10 − 0.20·(30 − CU)       при CU < 30
```

Вершина именно 9.88, не 10 — при `CU = 80` десятка получается округлением
компоненты, а не самой функции. Нижний излом (30) не откалиброван точно —
данные допускают диапазон 25–34.

**Веса `w1..w6` — макропараметры периода**, а не константы движка: ведущий
может менять их между периодами (в источнике встречались `50/10/10/10/10/10` и
`30/15/15/15/20/5`).

### 5.10. Занятость и отраслевые агрегаты

Формула занятости в источниках не опубликована. Реализована монотонная линейная
зависимость от выпуска с настраиваемыми коэффициентами:

```
Занято = round(baseStaff + Производство × staffPerUnit)     # дефолты: 0 и 1
```

Отраслевые агрегаты:

```
Средняя цена          = Выручка_индустрии / Всего_продано
Средняя себестоимость = Общее_производство_$ / Всего_произведено
Исп. мощности         = Всего_произведено / Общая_мощность
Продаж на служащего   = Выручка_индустрии / Всего_занято
```

Плюс изменения к предыдущему периоду в процентах (для «Складировано» — в штуках,
как в оригинальном отчёте).

### 5.11. Банкротство

Критерий: `Наличные < 0 И Займы >= абсолютный лимит`.

Сравнение нестрогое намеренно: при внешнем управлении заём упирается в лимит и
никогда его не превышает, поэтому строгое `>` не сработало бы ни разу.

Режим **«внешнее управление»** (дефолт): банк не выдаёт заём сверх абсолютного
лимита, фирма уходит в минус по кассе ровно на непокрытую часть. Эта величина
показывается отдельным полем `unfundedShortfall` — долг больше не растёт
бесконечно, но проблема видна. Метка банкротства не сбрасывается в последующих
периодах.

## 6. Разрешённые развилки и флаги

Источники восстанавливают оригинальный движок по косвенным данным и местами
противоречат друг другу. **Ни один спорный выбор не захардкожен.**

| Флаг | Дефолт | Альтернативы | Почему такой дефолт |
|---|---|---|---|
| `bankInterestFormula` | `official` | `flatLoanRate` | Подтверждена на реальном отчёте до доллара |
| `bankruptcyMode` | `externalManagement` | `freeze`, `labelOnly` | ТЗ требует не пускать фирму в бесконечный минус |
| `loanRepayment` | `preRevenue` | `none`, `sweep` | `preRevenue` воспроизводит финансирование до выручки и проценты на первоначально профинансированный долг по нативным SAVE HERMES1; старые сохранения остаются в прежнем режиме. `none` и `sweep` сохранены для архивных/пользовательских партий. При `sweep` погашение может увести заём в минус — это депозит (доход по `depositRate`) |

Спрос (11.A/11.B) и себестоимость раньше были спорными местами с двумя
несовместимыми версиями каждое — `mecom-spec.md` разрешил их однозначно
(реверс-инжиниринг сейвов и истории реальных партий), поэтому там больше нет
переключаемых флагов, есть одна формула.

Каждый оставшийся флаг покрыт тестом, который прогоняет партию из 4 фирм на 4
периода и проверяет, что расчёт не падает и баланс сходится.

## 7. Две формулы, выведенные при разборе

РИФ, дележ заказов, общий объём рынка и себестоимость откалиброваны напрямую по
`mecom-spec.md` (реверс-инжиниринг сейвов). Кэш-флоу и амортфонд сначала
восстанавливались по RLC; последующее сравнение с нативными SAVE подтвердило
режим финансирования `preRevenue` для новых игр (см. [CALIBRATION.md](CALIBRATION.md)).
Пример ниже — историческая проверка архивного режима `none`, не описание
стандартной новой игры.

### 7.1. Кэш-флоу

Официальная схема раздела 6 начинает расчёт с выручки, без входящего остатка
наличных, и формально запрещает одновременно иметь и кэш, и займы. В реальном
отчёте RLC фирма имеет **$51 096 наличных при $80 002 займов** — значит запись
неполна. Следующая сверка показывает, почему для этого архивного примера
использовали режим `none`.

Эквивалентная форма режима `none` — «револьверный» заём, который не гасится автоматически.
Входящий кэш восстановлен из тождества баланса на начало периода:

```
cash₀ + 0 + (873 × 40 + 30) = 80 002 + (−1 753 − 16 389) + 21 000
cash₀ = 82 860 − 34 950 = 47 910

ДП = 67 706 − 12 293 − 7 890 − 14 524 − 14 951 − 7 150 − 7 712 = 3 186
cash₁ = 47 910 + 3 186 = 51 096        ← ровно как в отчёте ✓
```

Совпадение до доллара. Дополнительный выигрыш: при такой записи тождество баланса
верно **по построению**, а не по счастливой случайности.

> В этом отчёте заём за период не изменился (`newBorrowing = 0`), поэтому
> входящий и закрывающий остаток совпадают, и банковский процент ($7 150)
> можно посчитать одним проходом. Это частный случай — пример ничего не
> иллюстрирует про саму итерацию из раздела 5.6 (проценты по вновь взятому в
> периоде займу); за неё отвечает отдельный тест
> `computePeriod.test.ts` («процент по займу учитывает и заём, взятый в этом
> же периоде»), где заём за период действительно растёт.

### 7.2. Остаток в амортфонде

В отчёте капвложения $48 153 при 1203 станках × $40 = $48 120. Разница $33
раскладывается как 30 (перенос с прошлых периодов) + 3 (остаток текущего:
13 203 − 330 × 40). Значит недоинвестированные доллары **копятся между периодами**,
а не сгорают:

```
Новые_станки = floor((Инвестиции_нетто + остаток₀) / 40)
```

Упрощённая формула из памятки (`мощность × $40`) даёт хорошее приближение, но не
точную копию движка.

Веса критериев РИФ живут здесь, а не в конфиге лиги — по источнику они меняются
между периодами, а не фиксированы на партию.

| Поле | Дефолт | Диапазон |
|---|---|---|
| `taxRate` | 0.25 | 0…0.99 |
| `bankRateBase` | 0.10 | 0…0.99 |
| `bankRateExtra` | 0.40 | — |
| `loanLimitBase` | 50 000 | 0…100 000 |
| `loanLimitAbs` | 100 000 | 0…100 000 |
| `rifWeightRetainedProfit` (w1) | 50 | 0…100 |
| `rifWeightDemandPotential` (w2) | 10 | 0…100 |
| `rifWeightSupplyPotential` (w3) | 10 | 0…100 |
| `rifWeightEfficiency` (w4) | 10 | 0…100 |
| `rifWeightMarketShare` (w5) | 10 | 0…100 |
| `rifWeightGrowth` (w6) | 10 | 0…100 |
| `scenarioNewsText` | пусто | свободный текст |

Макропараметры переносятся с прошлого периода при переходе к новому, кроме
новостного текста — его ведущий пишет заново.

### Стартовые условия фирмы

Дефолты масштабируются по числу фирм N в лиге: отраслевые итоги вводного сценария
раздела 4.1 источника (мощность 4200, займы 72240, накопленный НИОКР 3360) от N не
зависят, доля на фирму — итог/N (`makeFirmStart`, `src/engine/config.ts`). Для N=8
это даёт ровно пример источника: 525 станков (капитал $21 000), наличные $9 030,
заём $9 030, `initialRnd = 420`. Капитал всегда берётся равным стоимости станков
(`станки × machineCost`), а наличные — равными займу, поэтому тождество стартового
баланса сходится по построению при любом N, без ручной подгонки. Это пример
конкретной партии — ведущий правит цифры при создании лиги.

Той же логикой (`makeFirmDecision`) заранее заполняются решения периода 0: цена
$30 (не зависит от N — это параметр, а не итог), маркетинг и инвестиции-брутто —
8400/N, НИОКР — 3360/N. Для производства в источнике нет дефолта сценария, поэтому
берём 80% загрузки мощности периода 0 (оптимум себестоимости) — ведущему проще
поправить число, чем вводить его с нуля. Начиная с периода 1 все решения, включая
производство, наследуются с прошлого периода (`carryDecision`,
`src/state/leagueStore.ts`) — ведущий правит только то, что изменилось.

## 9. Модель данных

```
League
├── config: LeagueConfig            константы + featureFlags
├── firms: Firm[]                   стартовые условия
├── macroByPeriod: PeriodMacroParams[]
├── decisionsByPeriod: Record<firmId, FirmDecision>[]
└── results: PeriodResults[]

FirmOpeningState                    состояние на начало периода
├── machines, period0Machines
├── cash, loan, retainedEarnings, capital
├── inventory, inventoryUnitCost, inventoryAgedUnits
├── amortFundRemainder, employees
├── rndCumulative, rndDecayStock, retainedEarningsBase
├── productionPrevious, sharePrevious
└── isBankrupt

PeriodResults
├── firms: FirmPeriodResult[]       ~40 полей: решения, спрос, P&L, баланс, РИФ
├── industry: IndustryPeriodResult  агрегаты + дельты к прошлому периоду
└── macro: PeriodMacroParams
```

Менее очевидные поля `FirmOpeningState` заслуживают пояснения:

- `inventoryAgedUnits` — единицы, пролежавшие весь предыдущий период; только за них
  берётся плата за хранение.
- `amortFundRemainder` — недоинвестированные доллары, копятся между периодами.
- `rndDecayStock` — затухающий запас НИОКР для множителя объёма рынка (раздел
  5.2, мекомspec «Шаг 3»). Не путать с `rndCumulative` — тот вечный и служит
  только дележу долей (раздел 5.3).
- `retainedEarningsBase` — НакопПриб_база критерия C1 РИФ, фиксируется в
  периоде 0 и дальше не меняется.
- `productionPrevious` — произв_i,пред критерия C3 РИФ: производство этой же
  фирмы в прошлом периоде.
- `sharePrevious` — доля_i,пред критерия C6 РИФ: доля рынка (по сбыту) этой же
  фирмы в прошлом периоде, %.

## 10. Отчёты и экспорт

### Отчёт фирмы (приватный)

Моноширинный текст в две колонки по шаблону оригинала:

- **Слева** — P&L от выручки до чистой прибыли, затем заказы, продано,
  невыполненные, склад.
- **Справа** — решения периода, баланс, блок мощности (полная, доп. вложения,
  мощность следующего периода, использование, себестоимость единицы, занято, РИФ).
- Сверху — название фирмы, номер периода, дата. Снизу — новостной текст ведущего с
  переносом по ширине.

**Приватность обеспечена конструктивно:** рендерер принимает только данные самой
фирмы, чужие решения и P&L в него физически не попадают. Отдельный тест проверяет,
что уникальные суммы соперников не встречаются в тексте.

### Отраслевой отчёт (публичный)

Блок «Экономика» (ставки, лимиты, суммы займов, налог), блок «Индустрия»
(агрегаты с изменениями к прошлому периоду) и сравнительная таблица всех фирм:
Цена / Выручка / Ч.Приб / Н.Приб / Доля рынка / РИФ.

Фирмы в тяжёлом минусе показаны **текстовыми метками** (`Убытки`, `банкрот`,
`акц-ров:`) вместо чисел — как в оригинале. При большом числе фирм таблица
автоматически разбивается на блоки по 5 колонок, чтобы оставаться читаемой.

### Сводный отчёт (приватный, только для ведущего)

Третья вкладка на экране периода, поверх блока «Экономика» + «Индустрия»
(общего с отраслевым отчётом, `renderIndustryStats`): полная таблица по всем
фирмам разом — решения периода, цепочка «заказы → производство → склад →
сбыт → невыполненные», наращивание мощности, P&L/баланс и разбивка РИФ по
всем шести компонентам, плюс два рейтинга внизу (по РИФ и по чистой прибыли,
по убыванию).

**Без масок банкрота.** Это единственный отчёт, который не редактирует чужие
решения и не прячет цифры фирм в минусе текстовыми метками — он не рассылается
игрокам, его видит только ведущий, поэтому здесь всегда настоящие числа.

Два поля восстановлены расчётом, а не хранятся отдельно: остаток на складе на
начало периода (`Б/Склд`) — из тождества склада (`inventoryEnd − produced +
sold`), свободные средства (`СвобСр`) — наличные плюс неиспользованный остаток
кредитной линии до абсолютного предела с отсечением кредита на нуле.
Это итоговый отчёт, не бюджет ввода: последний сохраняет отрицательный кредит
и использует отдельные нативные стадии округления/усечения.

### Экспорт

У каждого отчёта две кнопки: «Копировать текст» (для мессенджера) и «Скачать как
изображение» (PNG через `html-to-image`, `pixelRatio: 2`). По умолчанию личный
отчёт склеивается с отраслевым блоком одним куском, как в оригинале; галочкой
отраслевой блок отключается — удобно, если ведущий постит его в общий чат один раз.

## 11. Хранение состояния

Партия сохраняется в `localStorage` под ключом `mecom.leagues.v1` автоматически
после каждого расчёта и каждой правки настроек. Перезагрузка страницы её не теряет.

**Экспорт/импорт JSON** — кнопка «Экспорт лиги в файл» на экране периода, импорт на
экране списка лиг. Формат версионирован (`schemaVersion`), импорт внятно ругается
на битый JSON, чужой файл, другую версию схемы и отсутствие состояния фирм.

Снимок содержит и саму лигу, и состояние фирм на начало текущего периода —
достаточно, чтобы продолжить партию на другом устройстве с того же места.

## 13. Известные ограничения

Формулы РИФ, дележа заказов, общего объёма рынка и себестоимости взяты из
`mecom-spec.md` — реверс-инжиниринга сейвов и истории 65 реальных партий, а не
реконструкции по конспекту. У самой спеки остаются помеченные `[НЕ
ОТКАЛИБРОВАНО]` места:

**Нижний излом `Eff(CU)` не откалиброван точно.** Взят как 30% загрузки, но
данные допускают диапазон 25–34: ниже 20% всего одна точка. Коэффициенты
0.136/0.102/0.20 проверены на одном сценарии — как `costCuUp`/`costCuDown` в
себестоимости, это, вероятно, параметры сценария, а не константы движка.

**Таблица `f(P)` грубая на участке 65–95.** Точки в этом диапазоне не
измерялись, там используется линейная интерполяция между 60 и 100. Коэффициент
`λ = 0.2076` подобран численно и может слегка дрейфовать: на одной серии
данных давал 0.195, на другой — 0.211.

**Объём рынка для неоднородной лиги выше цены 40 — известное смещение.**
`Всего_заказов = D(P̄)` точна при `P̄ ≤ 40` (отклонение ≤2% даже при разбросе
±20), но выше точки перелома `D(P)` даёт погрешность до +20% при сильном
разбросе цен (артефакт неравенства Йенсена на выпуклой кривой, а не осознанная
механика). Источник прямо говорит, что для клона это не обязательно
воспроизводить.

**Формула занятости выдумана.** В источниках её нет. Реализована монотонная
линейная зависимость от выпуска — она удовлетворяет единственному известному
требованию («растёт при увеличении производства, падает при снижении»), но реальная
формула движка может быть другой. Коэффициенты вынесены в конфиг.

**Решения нового периода не переносятся** с предыдущего — ведущий вводит их заново.
Это защита от случайного расчёта по устаревшим цифрам; если при живой игре
окажется утомительно, переносится одной правкой.

всё перечисленное добавляется без переписывания расчёта.
