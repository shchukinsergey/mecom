# Автоматизация оригинального МЭКОМ в DOSBox

`mecom-runner.ps1` играет за ведущего в настоящем `Mecompro.exe` (DOSBox), вводя
решения фирм по заданному сценарию цен и выгружая текстовый отчёт после каждого
периода. Цель — генерировать новые данные для калибровки формул в `mecom-spec.md`
(поверх уже использованных 65 партий/22 сейвов), не трогая интерфейс веб-клона.

## Требования

- DOSBox уже запущен с `Mecompro.exe` (окно `DOSBox 0.74-3 ... Program: MECOMPRO`),
  на главном экране лиги (`Лига «...», сыгран N период`).
- Игра установлена в папку, реально смонтированную DOSBox на диск Windows (обычно
  `...\MECOM v2.07\`), чтобы `Outgoing\<ЛИГА>\<ЛИГА>.Z0N` был читаем напрямую.
- Запускать через PowerShell 7+ (`pwsh`), не через `cmd`/старый `powershell.exe` из
  Git Bash — там были проблемы с типом `[ushort]` при вызове через `& script.ps1`
  из чужого раннера.

## Запуск

```powershell
$scenario = @(
    @(50, 65, 70, 75, 80, 85, 90, 95),   # период N: цена каждой из 8 фирм
    @(50, 65, 70, 75, 80, 85, 90, 95)
)
.\mecom-runner.ps1 -LeagueName "claud2" -Scenario $scenario -StartPeriod 1 `
    -OutCsv "..\..\data\calibration\claud2_p1_2.csv"
```

- `-StartPeriod` — это **реальный номер периода**, на который ляжет первая запись
  сценария. Берётся из главного меню игры: `сыгран N период` → `-StartPeriod (N+1)`.
  Автоопределения нет (не читаем текст с экрана OCR-ом) — указать неверно значит
  прочитать чужой/старый экспорт. Скрипт откажется работать, если файл экспорта для
  вычисленного периода уже существует (защита от этой ошибки).
- Каждый элемент `$Scenario` — это массив цен по фирмам **в порядке списка
  «Остались» на экране F2** (обычно совпадает с Фирма 1..N при чистом старте
  периода). Остальные решения (производство/маркетинг/инвестиции/НИОКР) скрипт не
  трогает — принимает то, что игра проставила по умолчанию (обычно значения
  предыдущего периода).
- После каждого периода скрипт проверяет, что свежевыгруженный отчёт действительно
  содержит текст «за N период» — если нет, останавливается с ошибкой (значит,
  двойной проход F2 не завершился, читай `screenshots/period_N_done.png`).

## Что важно знать про саму игру (иначе автоматизация ломается)

- **Стрелки/Tab не работают через обычный `SendKeys`/`keybd_event`** — DOSBox
  реагирует только на **сырые AT-скан-коды** через `SendInput` с
  `KEYEVENTF_SCANCODE`. Обычные клавиши (цифры, Enter, Esc, F-клавиши) работают
  через стандартный `SendKeys` без проблем. Уже реализовано в скрипте
  (`SendScanKey`), просто держи это в голове, если будешь его расширять.
- **Мышь в этом DOSBox не работает вообще.**
- **Фокус окна ненадёжен без проверки** — `SetForegroundWindow` из фонового
  PowerShell-процесса может тихо не сработать. Скрипт всегда делает трюк с Alt
  (`keybd_event(0x12,...)`) + `AppActivate` + проверку `GetForegroundWindow()` перед
  каждым действием.
- **Период не считается сразу.** Нужно дважды зайти в F2 «Принять решения»: первый
  раз — заполнить всех фирм и просто выйти (Esc, данные уже сохранены); второй раз —
  зайти снова (все фирмы уже «Приняли»), `Tab`-ом дойти до кнопки «Закончить ввод» и
  нажать Enter — только тогда игра считает период. Это поведение самой игры,
  подтверждено вручную пользователем, не баг автоматизации.
- **После сохранения отчёта (F1 → Z → Enter) экран не возвращается в главное меню
  сам** — нужно **два Esc** (один закрывает подтверждение сохранения, второй выходит
  из меню отчётов).
- Комплект отчётов **Z: S,I,A** уже настроен на вывод в файл (иконка дискеты) — не
  переключай устройство вывода, иначе вместо файла улетит на экран/принтер.

## Формат вывода

Каждая строка `.Z0N`-отчёта парсится позиционно (см. `Parse-Report` в скрипте) —
заголовок «Фирма N» ищется регуляркой, дальше построчно читаются известные поля
блока решений/результатов/РИФ. Повторяющиеся подписи (`Н.Приб` встречается и как
$-показатель, и как компонента РИФ) получают суффикс `#2`. Итоговый CSV — одна
строка на фирму на период.

## Известные грабли (уже наступили)

`data/calibration/claud1_period2_CORRUPTED_donotuse.csv` — пример испорченных
данных: второй прогон скрипта (до того как появились защитные проверки) не
дождался финализации периода, и следующий вызов F2 подмешал решения одного периода
поверх другого (цены `85/75` вместо задуманных `50/75`). Оставлен как образец,
**не использовать для калибровки**. С добавленными проверками (`-StartPeriod` +
файл-уже-существует + текст-периода-в-отчёте) это должно быть исключено, но
после каждого прогона стоит быстро сверять `Цена` в CSV с тем, что задавал сценарий.
